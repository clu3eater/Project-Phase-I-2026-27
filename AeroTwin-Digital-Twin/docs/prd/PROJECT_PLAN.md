| residual | vs. truth factor | correlation | healthy → degraded |
|---|---|---|---|

**Building it found two degradation-model defects that only appear over a full

making injectors the life-limiting item on every engine; in the trial fleet one
engine died at 356 h while its only injected fault was scheduled for 646 h and
never activated — baseline wear was drowning the faults the dataset exists to
teach. After the fix a healthy engine reaches TBO at CHI 0.756 and faults are
what cause early failure.

- ☑ `explain.py` — **exact** attribution, not SHAP. The composite health index

**Fusion result** (10 held-out engines): precision **1.000**, recall 0.878,
F1 0.935, false-positive rate **0.000**. Reported honestly — the autoencoder
*alone* scores a higher F1 (0.965), so fusion trades nine points of recall for
a zero false-positive rate. For an operator-facing alert surface that is the
right trade and not a close call: MIL-STD-411F 4.1.1a requires a healthy engine
to be silent, and an operator alerted on healthy engines stops reading alerts,
at which point recall stops mattering. The autoencoder's raw score stays
available to the maintenance view, where a false positive costs an inspection
rather than trust.

**RUL on held-out engines** (censored engines excluded — their recorded RUL is
a lower bound, not a value): LSTM RMSE **102.3 h**, R² 0.427, NASA score
**11.8 (target < 500, MET)**, late fraction 37 %. RMSE, MAPE and R² are **not
met** and are reported rather than tuned away. The combination is informative:
the model is not making systematically dangerous over-predictions, it is
imprecise. RUL depends on the *rate* of degradation, and a 30-sample window
spanning fifty seconds sees a state, not a rate. Closing it needs sequence
features that span sorties.

**Two classes remain weak, and the reason is inherent rather than fixable by
tuning.** Natural injector fouling and an injector *fault* produce the same
signature, differing only in rate — and rate is invisible inside a 30-sample
(50-second) window. The same is true of cooling wear versus cooling
degradation. Separating them needs the whole-life baseline that the RUL and
trend models see, not a short-window classifier. That is a statement about
where the discrimination belongs, not a defect in the classifier.

Seven defects found building this layer (DEV-51…57), the worst being that
**`OVERHEATING_TREND` had no implementation at all** — a required PS fault mode
that produced a ground-truth label and no physics, and had silently become a
duplicate of cooling degradation. Fixing it took that class from F1 0.092 to
0.586 and lifted macro-F1 0.565 → 0.652.

### Phase 4 — Layer 4: Twin Core  ◐ TWIN STATE + SHADOW MODEL COMPLETE
- ☑ `twin_state.py` — the twin's formal record. Pydantic v2, `extra="forbid"`,
  `validate_assignment=True`, so invalid state is rejected rather than stored.
  Four state categories per PRD Part 1 §6.2 (reported / desired / simulated /
  predicted) plus residuals, alerts, metadata and operational history.
  Channel validity from the ingest layer is **carried through, not discarded**:
  a residual computed from a stale reading is marked unusable, never averaged
  in as if it were zero.
- ☑ `shadow_model.py` — an as-new MVEM instance running alongside the real
  engine. **This is what makes it a twin rather than a dashboard.** Reusing the
  simulator's own outputs as the "prediction" gives a residual of exactly zero
  forever; the reference must be a separate instance with degradation pinned
  as-new and never advanced. Driven only by operating-point channels (throttle,
  rpm, altitude, OAT, airspeed) — never by an engine *response*, because
  feeding back measured CHT would let the shadow track the failing engine and
  the residual would collapse to zero exactly as the fault grew.
  Thermal states are seeded once from the first good frame (removes a
  multi-minute warm-up transient) and never re-seeded.
- ☑ 24 twin/shadow tests
- ☐ `registry.py` — twin registry, fleet view, lifecycle
- ☐ `storage.py` — SQLite/Parquet writer + Influx adapter
- ☐ `security.py` — JWT RS256, 4-role RBAC, audit log with integrity hash
- ☐ `twin_api.py` — FastAPI REST + WebSocket, OpenAPI
- ☐ `replay.py` — 4 replay modes + annotations
- ☐ `scenario.py` — what-if engine + Go/No-Go

**Residual-based detection proven** over four 900 s missions (1800 syncs each,
45/45 channels usable, data quality 1.000). Mean residual, measured minus
as-new shadow:

| condition (severity 0.8) | CHT | oil press. | EGT | inj. dev. | alerts raised |
|---|---|---|---|---|---|
| healthy | +0.6 K | +0.02 psi | +9.5 °C | 0.1° | **none** |
| cooling degradation | **+12.0 K** | +0.02 | +9.5 | 0.1° | **none** |
| lubrication issue | +0.5 | **+5.07 psi** | +9.2 | 0.1° | **none** |
| injector abnormal | +0.6 | +0.02 | **−28.5 °C** | **5.4°** | INJ TIMING DEV |

Two results matter here. First, **each fault moves one residual and leaves the
others at exactly the healthy value** — the residual vector is diagnostic, not
just a general "something is wrong" score. Second, cooling degradation and
lubrication issue are both caught **with no threshold crossed at all**: the
rule engine is correctly silent, and only the twin sees them. That is the
entire argument for building a digital twin instead of a limit monitor, and it
is now demonstrated rather than asserted.

Head-to-coolant gap widens 10.8 K → 19.4 K under cooling degradation while
coolant temperature itself stays flat (thermostat holds it) — the signature
that separates a fouled cooling path from a hot day.

### STRATEGIC READ — the direction is right, the balance now has to change

What is going well and should not be diluted:
- **Physics-first.** Most entries will train a network on synthetic data with no
  real engine model behind it. We have a model anchored to twelve published
  figures, including BRP-Rotax's own airflow-to-power relation to +0.09 %.
- **Provenance discipline.** Every engine number is tagged `[TCDS]`/`[OM]`/
  `[IM]`/`[MML]`/`[DER]`/`[MOD]`, and every departure from the PRDs is logged
  with evidence. This is what survives an expert's cross-examination.
- **A real HMI standard.** `PRD_Part4` binds the UI to MIL-STD-1472H and
  MIL-STD-411F. Very few entries will do more than style a dashboard.

The risk, stated plainly:
> The problem statement is titled **"AI-Enabled"**, and **none of the AI/ML
> layer, none of the edge layer and none of the UI exists yet.** All effort so
> far has gone into Layer 2. That was the correct foundation to lay first — the
> AI is only as good as the residuals the physics feeds it — but the balance
> must now shift decisively to breadth.

**Recommended next move: stop deepening the physics and build a thin end-to-end
vertical slice first** — CAN simulator → ingest → twin state → one Tier-1
detector → one live UI panel — before deepening any single layer. A system that
demonstrably moves end-to-end at 30 % depth beats one perfect layer and four
empty ones, and it de-risks every integration assumption while there is still
time to change them.
